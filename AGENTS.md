# faberlang.dev — Agent Guide

**Workspace work mode.** Ordinary development is **direct** in this
checkout on `main`. Worktree packets under `../worktrees/<lane>/` are
optional Tugboat isolation. Do not stand up lanes unless the operator
asked. Container law: [`../AGENTS.md`](../AGENTS.md).

## What this repo is

The faberlang.dev documentation site. Contains Markdown source pages, the
Speculum site generator (written in Python), and the deployment pipeline for
the live website at https://faberlang.dev.

## Deployment architecture

### DNS and serving

| Layer | Detail |
|---|---|
| **Domain** | `faberlang.dev` |

| **Server** | GitHub Pages |
| **Worker** | None in this checkout. DNS points to GitHub Pages. |

### Deploy workflow

The live site deploys from `origin/main` via GitHub Actions:

1. **Trigger:** Push to `main` branch
2. **Workflow file:** `.github/workflows/deploy-pages.yml`
3. **Artifact:** Uploads the committed `dist/` directory as a GitHub Pages artifact
4. **Deploy:** `actions/deploy-pages@v4` publishes the artifact

### What is live now

The site is generated from Markdown sources through the Speculum generator.
The deploy pipeline is:

1. **Local render:** `generator/scripts/build-site.sh` (a launcher for
   `build.py`) renders only `src/en-US/` to `dist/en-US/`, writes root IA
   redirects and retired-locale meta-refresh aliases, and runs gates
2. **Commit:** `dist/` is committed to the repo. The renderer is Python;
   source generation may call the Faber CLI locally.
3. **Deploy:** Push to `main` triggers `.github/workflows/deploy-pages.yml`,
   which uploads `dist/` as a GitHub Pages artifact and deploys it

**URL scheme (Decision 18a):** content lives at `/{locale}/…`
including English (`/en-US/…`). Root `/` is the **locale-less landing page**
(`dist/index.html`), generated by `generator/scripts/generate-landing.py`
(not the Markdown pipeline): the claim, an agent pass that hands the reader's
model `faberlang.dev/install.md` (copy buttons), one program in every reader
locale with its real output, a locale strip linking English to its docs and reader packs to locale-mapping pages,
the cross-compile proof (real `radix emit` output plus a capability table parsed
from `faber targets`), the libraries, and the grammar size (read from the
EBNF). The hero has no canvas or ambient animation; `faber-instrument.js` is
its only script (clock + copy buttons), and the page works without it. The
favicon data URI is defined once in `generator/scripts/site_assets.py`
and shared by the renderer, landing, and portal generators. Its code panels
are compiler output captured by `generator/scripts/capture-landing-panels.sh` into `generator/landing/` — run
that, never hand-edit a panel. The full language chooser lives at `/porta/`
(`generate-portal.py`; panels from `generator/portal/exemplars/`). Retired
English-at-root content paths still redirect via `<meta http-equiv="refresh">`
stubs (the landing and portal `index.html` files are exempt). Agent surfaces (`/llms.txt`,
`/agents/`, `/.well-known/`) stay locale-less at the site root.

**To update the live site after content changes:**

```bash
# 1. Render all pages (includes post-build gates, sitemap, canonical tags)
bash generator/scripts/build-site.sh

# 2. Commit both source and rendered output
git add src/ dist/ static/
git commit -m "content: update pages"
git push origin main
```

The push triggers the deploy automatically. GitHub Pages typically updates
within 1-2 minutes. The build halts on any gate failure (broken links,
leakage, missing discovery surfaces).

## Speculum generator

### How it works

The renderer is one Python module, `generator/scripts/speculum_py.py`, shared
by the authored-page, corpus, and alias modes. There is no Faber generator
package or compiled generator binary. U4 builds only the English source tree.
It converts
Markdown → HTML with:

- Block-level parsing (headings, paragraphs, tables, lists, code blocks)
- Inline span rendering (backtick code, bold)
- Heading anchors (`{#kebab-case-id}` syntax)
- Frontmatter extraction
- Shared stylesheet injection

### Render pipeline

```bash
# Incremental build against the pinned radix (default)
bash generator/scripts/build-site.sh

# Wipe dist and the manifest, rebuild everything
bash generator/scripts/build-site.sh --full

# Move the radix pin, then regenerate everything that derives from it
bash generator/scripts/build-site.sh --refresh-upstream [REV]

# Render a single page (site_locale, reader_locale)
generator/scripts/render.sh src/en-US/syntax/types.md en-US la /speculum.css output.html

# Validate all code fences
generator/scripts/validate-fences.sh src/en-US
```

`build.py` is one process. Per-page work (staleness, reader-locale conversion,
rendering) runs in-process; only the whole-tree generators and presentation
passes are spawned. Every output records the SHA-256 of its inputs in
`generator/target/build-manifest.json` (disposable, ignored by Git), so a build
with nothing changed renders nothing and an edit to one page renders that page.
Incremental output is byte-identical to `--full` (checked 2026-10-14).

**Measured times, 2026-10-14** (18-core laptop under load average ~6–9, pinned
radix 20c62a89c7):

| Run | Time |
|---|---|
| `--full` (corpus and convert cache cold) | ~6 s |
| `--refresh-upstream --full` (adds 197 `faber explain` calls) | ~26 s |
| no change | ~1.6 s |
| one authored page edited | ~1.5 s |

The previous driver measured 142 s for `--full`, 17 s no-op, 17 s one page on
the same machine: about 8,000 subprocess spawns, 375 of them a manifest check.
A build that exceeds these by 3x is a finding, not a fact of the environment.

### The radix pin

The build never reads the live radix checkout. It reads `grammar/`, `locale/`
and `corpus/` as of the git tree ids in `generator/upstream.lock.toml`,
extracted by `git archive` to `generator/target/upstream/radix/` and reached
through `upstream.radix_root()`. Radix `main` moves many times a day, and a
grammar addition used to fail the build at step 0; now it cannot touch the
site until you move the pin.

`build-site.sh --refresh-upstream [REV]` is the only thing that moves it. It
re-pins (default `HEAD` of `../radix`), snapshots `faber explain --list` to
`generator/upstream/explain-list.txt`, regenerates the agent reference
(`generate-agent-reference.py`, the only step that needs a compiler with a
reference pack: it prefers `../radix/target/debug/faber`, then `faber` on
PATH), and re-runs every generator and the corpus. Commit the lock, the
snapshot, and the regenerated `src/`, `static/` and `dist/` together.
Tree ids are content addresses, so a radix history rewrite that only changes
commits leaves the pin valid.

`faber` on PATH (or `--faber`) is used for reader-locale conversion. Results
are cached in `generator/target/convert-cache/` keyed by compiler version,
reader pack tree, source locale and source text.

### Degraded fallbacks

A generator that cannot do its job exactly used to print a warning and carry
on with a cruder result, and the build still exited 0. Every fallback is now a
recorded event (`receipt.degraded`, or a `DEGRADED <kind> <subject>: <detail>`
stderr line from a standalone script). Events are stored on the output they
affected, so unchanged pages keep reporting them, and the build ends with a
count and `generator/target/build-receipt.json`.

The build fails on any event that `generator/degraded.allow.toml` does not
list with a `why`, and under `--full` on any entry that matches nothing. Fix
the cause or add a truthful entry; do not add an entry to make a build pass.
A mermaid fence with no cached SVG is such an event: the build does not
install node dependencies or download a browser. Run
`python3 generator/scripts/diagrams.py render` and commit the SVG.

### Generated source pages

Some pages under `src/` are **not authored** — they are assembled from the
pinned radix trees and captured panels before the render (the `[generators]`
phase of `build.py`). Editing them by hand works until the next build
overwrites the edit; change the generator or the upstream source instead.

| Script | Writes | Reads |
|---|---|---|
| `generate-target-matrix.py` | `src/en-US/toolchain/target-matrix.md` | `radix/grammar/EBNF_MATRIX.md` + English target strings |
| `generate-grammar` (native Faber gate) | `src/en-US/reference/grammar.md` (then reshaped by `generate-grammar-tree.py`) | `radix/grammar/EBNF.md`, grammar sources, English glossary, `radix/locale/en/pack.toml` |
| `generate-grammar-tree.py` | `src/en-US/reference/grammar.md` (family overview), `src/en-US/reference/grammar/*.md` (term tables, no EBNF), `static/agents/grammar/productions.md` (+ `dist/` copy; the full English-spelling EBNF) | same radix grammar inputs as `generate-grammar`, plus `dist/en-US/corpus/` for term links |
| `generate-target-lanes.py` | `src/en-US/targets/*.md` | captured lane panels |
| `generate-localization.py` | `src/en-US/localization.md` | locale registry + captured panels |
| `generate-releases.py` | `src/en-US/releases/*.md` | `gh` release tags + sibling `docs/release/v*.md` |
| `generate-agent-locales.py` | `static/agents/locales.md`, `dist/agents/locales.md` | `radix/locale/*/pack.toml` |
| `generate-agent-reference.py` | `static/agents/reference/`, `dist/agents/reference/` | `faber explain --list` and `faber explain <term> --json` |

`generate-agent-reference.py` mirrors the compiler's explain registry: one page
per entry, plus alias stubs and a section index. It needs a `faber` binary that
resolves its reference pack — an installed binary carries none unless one was
installed beside it — so it prefers `radix/target/debug/faber` and accepts
`--faber`. It uses the compiler as a tiebreaker on its own output: projection is
a token rewrite, and because Faber allows a keyword as an identifier a rewrite
can break code that prose survives, so each example ships in whichever form
`faber check --locale=en` accepts. Slugs come from the reader pack, and the
first term in sorted order keeps a contested slug; the loser falls back to its
own name and then to a numeric suffix.

`generate-agent-locales.py` is the one generator that writes an agent static
surface rather than `src/`, so it runs in step 0 ahead of the static copy. It
joins the eight reader packs on the canonical key, ordered `English | Latin |
ar | hi | th-TH | vi | zh-Hans | zh-Hant`. `--strict` fails on drift that is
neither a designed shape nor the expected list in
`generator/scripts/agent_locales.py`; the designed shape is `la` carrying no
`[intrinsics]` section, which
`radix/crates/radix-module/src/intrinsic_pack_completeness_test.rs` asserts, and
the expected list is the pack drift owned by a compiler-side fix.

A generator whose declared inputs are unchanged is skipped. **`generate-releases.py`
is not part of the build**: it needs `gh` and network access. Run it by hand
when a release lands.

### Post-build validation scripts

`build-site.sh` runs these automatically as fail-closed gates on the top-level
build. They can also be run standalone. The link gate permits only the six future U5
locale-mapping targets as explicitly deferred links; the retired URL walker
separately proves every alias and its target:

| Script | Purpose | Exit |
|---|---|---|
| `check-internal-links.py` | Verifies every internal `href` target exists in `dist/` | 1 on broken links |
| `check-leakage-gate.py` | No English→locale nav leakage; all locale pages carry honesty notice | 1 on gap |
| `generate-sitemap` | Generates `dist/sitemap.xml` from maintained English HTML; alias stubs are skipped | — |
| `inject-canonical.py` | Injects `<link rel="canonical">` into pages missing one | — |

### Presentation post-process

These run after chrome injection and before the gates. All are idempotent and
operate on rendered HTML, so none of them requires a generator rebuild.

| Script | Purpose |
|---|---|
| `diagrams.py render` | Renders ```` ```mermaid ```` fences in `src/` to `generator/diagrams/<hash>.svg` |
| `diagrams.py inject` | Inlines those SVGs into `dist/` as `<figure class="diagram">` |
| `highlight-code.py` | Wraps tokens in fenced `faber`/`bash`/`toml` blocks in `.tok-*` spans |
| `inject-toc.py` | Gives headings ids + `#` self-links, adds the per-page contents rail |
| `tag-glyph-chips.py` | Adds `class="glyph"` to inline `<code>` holding only a glyph (1-4 characters, no ASCII letter or digit), which the stylesheet sizes up; fences are skipped |
| `inject-pass.py` | Replaces a `<p>::agent-pass::</p>` marker with the agent pass card (the same component the landing renders, from `agent_pass.py`; strings from the locale's `chrome.toml` `[pass]`). The Start page carries the marker in every locale. Runs after `inject-toc.py`; fails closed when the marker is present but the pass cannot be built |
| `matrix-cells.py` | Target matrix pages: restores the escaped term anchors (`<a id>`) from the upstream matrix as real anchors and adds `st-ok`/`st-warn`/`st-no`/`st-defer` to glyph cells (✓ ◐ ✕ ○ —) |
| `locale-tabs.py inject` | Swaps cheat sheet and target-lane Faber blocks for reader-locale tab cards |
| `localize-spans.py` | Renders inline `.kw`/`.typ` terms in the page's reader locale |

**Reader locale.** The maintained prose tree is English (`locales.toml` maps
`en-US` → `en`). Latin remains the canonical source surface and compiler
interchange dialect. Reader locales surface through the locale chooser, the
per-language mapping pages, reader-locale tab cards on fences marked
`locale-tabs` (U6), and the CSS-only keyword-spelling toggle on the grammar page
(U7, `grammar-toggle.py`).

| Layer | Handled by |
|---|---|
| Fluid and eligible pinned/text Faber fences | `localize-markdown.py`, before the render |
| All Markdown terms and corpus examples | `project-reader-terms.py` and the corpus bundle wrappers |
| Cheat sheet / targets fences | `locale-tabs.py`, current captured 8-locale cards defaulting to `en` |
| Remaining single-token `` `term` `` spans in prose | `localize-spans.py`, after the render |

`speculum_py.py` resolves each inline span against a closed set — 37 keywords + 13
types — and emits `class="kw"` or `class="typ"`; `localize-spans.py` swaps the
spelling. Compounds are projected by token rules that refuse paths
(`norma:textus`, `solum:lege`), anchors, production ids (`itera_stmt`),
hyphenated names (`device-summa`, `non-null`), and quoted strings. The English
word `in` stays in prose and in comments, except when a comment names `` `in` ``,
`` `per` ``, or `` `est` `` as a keyword. Inside Faber code, `in` / `per` / `est`
become `mut` / `step` / `is` when the span also contains another Faber term,
and `non est` becomes `is not`. `T ∪ nihil` can become `T ∪ none`.

A page may set `translate_spans = false` to skip only the HTML span pass.
The maintained English pages use English keywords. Markdown projection still
runs either way. Grammar remains skipped by span localization because its
generated productions retain their bilingual contrast and production ids.

**Diagrams.** The SVG cache is committed, so a build without Node still
produces a complete site; `render` is a source-side authoring step and
`inject` only ever reads the cache. A diagram with no cache entry stays a
readable code block rather than failing the build. Colours are not baked in:
`render-mermaid.mjs` feeds Mermaid sentinel colours that `diagrams.py`
rewrites to `var(--…)` tokens, so diagrams follow light/dark with the page.
After adding or editing a `mermaid` fence, run:

```bash
python3 generator/scripts/diagrams.py render
```

which installs its own Node dependencies under `generator/target/` on first
use. Commit the new `generator/diagrams/*.svg` alongside the Markdown.

**Reader-locale tabs.** A Faber fence marked `locale-tabs` renders as a tabbed
card carrying all eight reader surfaces (the cheat sheet and target lanes use
them). Like the diagram cache, the panels are committed so a build without the toolchain still
produces a complete site — `inject` only ever reads the cache, and a missing
panel set leaves the plain Latin block in place.

A fence marked `mode=package` is skipped: it is one file of a multi-file
package, so `faber format` cannot resolve its siblings and there is nothing
honest to render. Those blocks stay as plain source.

After editing a Faber fence in either section, run:

```bash
python3 generator/scripts/locale-tabs.py render
```

and commit the resulting `generator/locale-tabs/*.fab` alongside the Markdown.

`render` transcodes with `faber format --locale`, which resolves reader packs
relative to its own binary. A workspace build has no `share/faber/locale/`, so
the script links the packs from the Radix tree into place on each run — inside
`radix/target/`, which is build output. Without that every locale fails with a
pack-not-found error while still exiting 0.

It also caches each pack's keyword vocabulary as `vocab.<locale>.json`.
`highlight-code.py` prefers those over the generated search indexes, which
carry Latin canonical terms — the `en-US` index has two localized spellings, so
an English panel's keywords would otherwise go unpainted.

**Contents rail.** `inject-toc.py` reads its label from the page locale's
`chrome.toml` `[toc].heading`. The maintained tree is `en-US`; retired locale
paths are aliases, not translated pages.

**Heading ids.** The generator only emits an id when the Markdown spells one
out as `{#anchor}`. `inject-toc.py` derives a slug for the rest so every
heading is linkable; explicit anchors are never overwritten.

The corpus renderer (`render-corpus-batch.sh`) also post-processes its output:
- Writes each term page under the reader-pack slug (`fn.html` on `en-US`);
  the Latin identity key stays as a static alias redirect (`functio.html` → `fn.html`)
- Remaps leftover Latin related-link hrefs onto those slugs
- On slug collisions, keeps the first sorted identity on the pack slug and
  leaves later identities on their Latin keys with a build warning
- Suppresses dead cross-reference links (converts to plain text)
- The maintained `en-US` corpus has no translation-status banner; retired locale corpus URLs are handled by the alias manifest

**Retired locale URLs.** The six former prose trees are removed. Their committed
URL inventory is `generator/redirects/retired-locales.toml`; every path is
served as a meta-refresh stub to an English page, a corpus slug page, or the
nearest family index. `retired-locales.py check` verifies full coverage and
that every refresh target resolves. The sitemap and search index contain only
the English tree; `/llms-full.txt` is a locale-neutral corpus reference.

### Binary versions

- **Content targets radix HEAD, not a release.** The site is not published until
  the next release, so every page is checked against the radix commit recorded in
  `generator/upstream.lock.toml` and a `faber` built from that commit. Pass it
  with `build-site.sh --faber <path>`: the convert cache is keyed on the binary's
  content hash, so two builds that both print `faber 1.13.0` never share entries.
  A claim that holds for the previous release but not for HEAD is a defect.
- **The install surface pins the published release.** `static/install.md`, the
  install skill and the skill catalog name one release. They are the only
  hand-typed release facts. At a publish run
  `generator/scripts/bump_release.py <version> --published <date> --radix <version>`
  (it rewrites the version, tag, date, bundled compiler and the four archive
  URLs together; `--check` verifies the three files agree and a test pins it),
  update this note, build, commit. Nothing else on the site carries a version.
- **Ruled but not built at HEAD.** These are not stated as fact anywhere; each
  has a sentence that is true today and must be revisited when the item lands:
  the anonymous `record` literal (`language/types.md` "no anonymous object"
  sentences and `cheatsheet/types.md` on `:` versus `=`); `reduce via first`
  replacing `primus_quem`/`ubi` (the generated locale rows); `trapped<R,T>`,
  flat `ERRnnn` codes and no run-time message text (`language/errors.md`);
  removal of `FABER_LIBRARY_HOME` (the pages already say `--library-home`).
  `rg -n "primus_quem|no anonymous" src` finds the first two.
- Check against the HEAD binary, not an older build or a release tag. Holding a
  HEAD fact back "until the release" is a second content pass at publish.
- The GPU pages state mechanism only: `@ kernel`, `[device]`, `faber run
  --device`, fail-closed codes, and what `faber targets` says each device target
  emits. The landing build gate requires "device inference is not shipped" and
  "fail-closed". There are no measured "proven" claims: the device fixtures in
  `examples/` did not check at HEAD (`SEM056`), the cited harness is retired,
  and the gpu-reset campaign records no product path. Do not reintroduce a
  status table without a run on the current tree.
- **Renderer:** `generator/scripts/speculum_py.py` is the single Python
  implementation for page, corpus, and alias rendering. `build.py` imports it;
  `render.sh` calls it directly for a single page. The build driver needs
  Python 3.11+ (`tomllib`).

## Rules for agents

- **Never merge to main without a deploy workflow.** The old workflow was
  deleted; merging without a replacement will blank the live site.
- **Never commit `generator/target/` or `.DS_Store`.** See `.gitignore`.
- **Faber comment rule:** `#` only, on its own line. No inline comments
  (`//` or trailing `#`). Violations throw `LEX006`/`LEX007`.
- **Code fences in Markdown must pass `radix check`.** Run
  `validate-fences.sh` after editing any Markdown with fenced Faber code.
- **One stylesheet.** All CSS lives in `generator/www/speculum.css`. The
  generator cannot write CSS. Do not inline styles in pages.
